# Задачи по ролям — полный чек-лист функционала бэкенда

Ниже — ВЕСЬ функционал, который отдаёт бэкенд (он полностью готов и в `main`),
разложенный по тому, какая роль должна его показывать. Отмечено, что уже
сделано, что в процессе, что ещё не тронуто. Цель: чтобы к сдаче каждый
экран использовал реальные данные бэкенда, а не моки/localStorage.

Полный API-контракт с примерами запросов — в `CLAUDE.md` (секции v1–v4).
Правило: пушить прямо в `main`, не в свои ветки.

Что доделать:

   Демо-пароль у всех: `usta1234`. При успехе (200) сохрани весь объект
   мастера в `localStorage`, покажи имя в шапке вместо выпадающего списка.

2. **"На линии / не на линии"** — уже реализовано (`POST /api/masters/:id/duty`),

5. **Scheduled-записи** — в очереди могут приходить записи со
   `status: "scheduled"` и полем `scheduledFor` (клиент записался не на
   сейчас, а на конкретное время) — показать их отдельной строкой с временем,
   без кнопок действий (они сами перейдут в live-очередь по времени или через

**Статус: дизайн готов, нужно подключить реальные данные вместо моков.**

Один эндпоинт закрывает почти всё: `GET /api/owner/today` →

3. "Мастеров на линии" — сейчас у тебя это моковое число (`activeMasters`
   из мока). Замени на `onDutyMasters` из `/today` и подпиши как
   `${onDutyMasters} / ${totalMasters} на линии`.
4. **Сотрудники/зарплаты** — сейчас это отдельная localStorage-система

   `salaryPercent` на каждом мастере. Для колонки "начислено сегодня" по
   каждому мастеру — `GET /api/masters/:id/today` → `earned` (отдельный

5. Салоны (мультисалонность) — `GET /api/salons` — если успеваешь, добавь

## @Elyor2011 — Клиент (`/frontend-queue`)

**Статус: ещё не начато — это сейчас риск #1 для демо.**

Не dashboard, а лендинг-стиль (см. отдельное сообщение с требованиями по
дизайну/палитре). Полный флоу от начала до конца:

1. **Салоны** — `GET /api/salons` → карточки (название, адрес, при желании
   координаты на карте). Клиент выбирает салон.
2. **Мастера салона** — `GET /api/masters?salonId=<id>&onDuty=true` —
   ВАЖНО: фильтр `onDuty=true` обязателен, иначе клиент сможет записаться к
   мастеру, который не пришёл на смену. Карточки с фото (`photoUrl`, пока
   пустой — можно заглушку).
3. **Услуга** — `GET /api/services` → список с ценами, клиент выбирает одну.
4. **Когда** — две кнопки: "Встать в очередь сейчас" или "Записаться на
   время" (показать `datetime` picker, только будущее время).
5. **Создание записи** — `POST /api/queue`
   `{ clientName, phone, serviceId, masterId, scheduledFor? }`. Если
   `scheduledFor` не передан — обычная живая запись (`status: waiting`),
   клиент сразу видит номер и ETA. Если передан — `status: "scheduled"`,
   ETA не считается, вместо этого показать "вы записаны на HH:MM".
6. **Подтверждение / booking-код** — после создания записи покажи клиенту
   крупно её `_id` (booking-код) — "покажите этот номер ресепшну". Это
   замена настоящему QR-сканированию, достаточно для демо.
7. **Свой статус в реальном времени** — подключись к тому же Socket.io
   (`API_URL`), слушай `queue:update`, фильтруй по своему `_id` в массиве
   `queue`, обновляй позицию/ETA на экране без перезагрузки. Если `paid:true`
   пришло в объекте — покажи "✅ Оплата подтверждена".
8. **"Я пришёл раньше времени"** (для scheduled-записей) —
   `POST /api/queue/:id/checkin` — переводит запись в живую очередь прямо
   сейчас, не дожидаясь `scheduledFor`.

Если время совсем поджимает — пункты 1–6 обязательны для демо (это и есть
"клиент записался"), 7–8 можно урезать/упростить до одной строки текста.
